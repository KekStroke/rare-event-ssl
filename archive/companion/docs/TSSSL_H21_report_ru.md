# H21: событийная ветка в предобучении HuBERT. Отчёт по решающему эксперименту (2026-10-19)

## Постановка
Три режима предобучения (modern-блок, 20k шагов, синтетические смеси из лабораторных клипов), одинаковая событийная голова (наличие, onset, лог-длительность), одинаковый FT на полевых метках тренировочных фолдов (1.5k шагов), одинаковый декодер экземпляров (пики onset + предсказанная длительность, перекрытия разрешены), пороги подбираются только на dev под бюджет 100 FA/ч. По три сида.

| Режим | Предобучение |
|---|---|
| R1 | только единицы km(AVES); событийная голова появляется на FT |
| R2 | единицы + событийная ветка (вес 1) |
| R3 | только событийная ветка, без потери по единицам (контроль) |

Критерий: class-agnostic strict recall (tau 0.5) при сопоставимом тестовом FAR; отдельно recall на перекрывающихся референсах (119 из 613).

## Как читать числа: 0.072 против 0.066
Разность средних по сидам в рабочих точках 0.871 − 0.799 = 0.072 и бутстрэп-оценка +0.066 измеряют разное и агрегируют по-разному (check_aggregation.py):
- рабочие точки выбраны на dev и имеют разный тестовый FAR (106 против 90); бутстрэп этой же величины даёт +0.072 [+0.043, +0.103], то есть совпадает;
- «recall при FAR 100» берётся с кривых, где главный порог декодера (th_on для экземпляров, detect для кадров) прогоняется по сетке, а вторичные параметры (d_min, min_score / edge) остаются теми, что выбраны на dev для данного фолда; кривые считаются одинаково для всех режимов, dev-точки в них не подмешаны;
- среднее по сидам от интерполяций по отдельным прогонам (decode_instances: 0.873 − 0.801 = 0.072) против интерполяции объединённой по сидам и записям кривой (отношение сумм: 0.870 − 0.802 = 0.068) против среднего бутстрэпа (+0.066): различия только в способе агрегации, mean-of-ratios против ratio-of-sums, и в бутстрэп-смещении;
- в первой версии у 34 % бутстрэп-выборок R2 кривая не доставала до FAR 100 (минимальный th_on 0.05), и определённые выборки были смещены к высокому FAR; сетка расширена вниз до 0.005, теперь неопределённых выборок ≤1 %, числа выше даны по расширенной сетке.

## Вердикт
1. **Гипотеза H21 в исходной формулировке не подтвердилась.** Совместный режим (R2) не лучше контроля без HuBERT-цели (R3): разность +0.019 с интервалом [−0.004, +0.042]; на перекрывающихся вызовах разности нет.
2. **Что действительно работает.** Обучение событийной ветки уже на предобучении даёт +0.066 recall при FAR 100 против той же головы, добавленной только на FT. Декодер экземпляров даёт самый большой эффект: +0.10…+0.16 recall при равном FAR. На перекрывающихся вызовах внутри основной таблицы (R1 → R2, оба с декодером экземпляров) recall 0.638 → 0.723; переход 0.24 → 0.72 относится к смене декодера на тех же прогонах (покадровый → экземпляров, R2, рабочие точки dev≤100) и должен подписываться именно так.
3. **Дополнительная польза HuBERT-цели в H21 не обнаружена.** Контроль R3 (супервизированное предобучение на синтетике без SSL-потери) не хуже, с покадровым декодером чуть лучше R1 (+0.030 [+0.006, +0.060]). Это не доказывает ненужность цели вообще, но в данном протоколе позволяет предпочесть более простой R3.
4. **Voxaboxen.** Его сохранённые предсказания доступны только от порога 0.5, максимальный FAR 61/ч при recall 0.816. R2 и R3 при 61/ч дают 0.847 и 0.849, разность +0.04 с интервалом [−0.05, +0.17]: не разрешено. В рабочей точке dev≤100 Voxaboxen достигает лишь 0.697 при FAR 43. Честное сравнение требует Voxaboxen, дообученного на полевых метках, как наши модели.

## Оговорки
- Рабочие точки R2 и R3 превышают dev-бюджет (106 и 128 против 100): перенос порога dev→test хуже, поэтому первичны числа при согласованном FAR.
- Событийная ветка использует метки конструкции синтетики. Это дополнительная супервизия, а не чистый SSL. Корректная формулировка результата: «супервизия экземпляров из синтетической конструкции плюс декодер экземпляров», а не «новый HuBERT».
- Все три режима используют modern-блок. Проверка H22 (R3 на vanilla против R3 modern, три сида): vanilla по сидам 0.869 / 0.825 / 0.786 против modern 0.905 / 0.902 / 0.853 в рабочей точке; recall@100 по объединённой тестовой кривой 0.844 против 0.885. Парные разности по записям: в рабочей точке −0.060 [−0.079, −0.039], при FAR 100 −0.050 [−0.114, −0.018], при 150 −0.049 [−0.076, −0.026], на перекрывающихся −0.068 [−0.103, −0.036]. С покадровым декодером разница −0.021 [−0.043, +0.000], на грани. Вывод: современный блок измеримо помогает именно событийному детектору, тогда как покадровому детектору на единицах HuBERT он не помогал. Это закрывает только данную комбинацию компонентов при данном бюджете; какой из компонентов блока отвечает за эффект, не атрибутировано.
- Утверждение «modern-блок стабилизирует обучение непрерывных целей» остаётся объяснением наблюдаемого эффекта data2vec (+0.19 на probe), устойчивость отдельно не измерялась.
- Ближайший метод Voxaboxen тоже обучается на синтетике и предсказывает onset/длительность; «синтетические метки + onset и длительность» новизну не устанавливают. Отличия и протокол честного сравнения: TSSSL_voxaboxen_protocol_ru.md.
- 17 записей, 613 референсов; интервалы широкие, но знак эффектов R2−R1 и экземпляры−кадры устойчив по всем сидам.

Чтение:
- **Преимущество зависит от бюджета ложных тревог.** При малых и средних бюджетах (≤100 FA/ч, рабочий диапазон для Ольги) детектор с предобученной веткой экземпляров впереди: при 61 FA/ч интервалы обеих систем R2 и R3 не содержат ноль, при 100 FA/ч ноль исключён для R3 и почти исключён для R2. При 150 FA/ч паритет, при 300 FA/ч Voxaboxen-FT номинально впереди на 0.02–0.03, не разрешено.

Объяснение остаётся гипотезой: паросочетание fwd/bck само по себе перекрывающиеся интервалы не запрещает (оно лишь сопоставляет предсказания двух направлений), кандидаты на причину это soft-NMS внутри направления и обучение на синтетике без перекрытий; второе проверяется абляцией H24, первое отдельно не отделено.
- **R1 (только единицы) с Voxaboxen-FT не конкурирует:** при 100 паритет, при 300 проигрыш −0.121. То есть против сильного аналога работает именно предобученная ветка, а не декодер сам по себе.
- **Полевой FT изменил Voxaboxen неожиданно:** при 61 FA/ч он стал хуже своей synthetic-версии (−0.121 [−0.204, −0.044]), зато кривая при больших бюджетах поднялась до 0.945. Одна из причин ниже.

Оговорки по Voxaboxen:
- Штатный пайплайн оценивает последнюю эпоху: «early stopping» в пакете действует по train-loss, model.pt перезаписывается каждую эпоху, final-model.pt это веса после последней эпохи. Лучший val-F1 достигался раньше (эпохи 15–25 в первом проходе). Второй проход с сохранением лучшего валидационного чекпоинта (локальный патч train.py; лучшие эпохи 19 / 42 / 25) дал более слабую модель по нашему критерию: рабочая точка 0.685 при FAR 76, recall@61/100/150/300 = 0.653 / 0.764 / 0.842 / 0.935, везде ниже последней эпохи (разность при 61 −0.043 [−0.089, +0.001]). Возражение «соперник переобучен» снято: отбор по val-F1 выбирает эпоху, ориентированную на точность, которая хуже по recall при фиксированном FAR. В заголовочной таблице используется более сильный вариант Voxaboxen (последняя эпоха, штатный пайплайн). Против варианта с лучшим чекпоинтом наши разности больше: R2 при 61 +0.185 [+0.092, +0.286], при 100 +0.101 [+0.019, +0.199]; R3 при 100 +0.119 [+0.043, +0.204].
- Один сид Voxaboxen против трёх наших; энкодер 90M против 17.8M; обучающих полевых данных на фолд 0.6–0.9 ч.
- Четыре локальных патча в инференсе Voxaboxen 0.2.0 (задокументированы), алгоритм декодера не менялся.

## Роль перекрытий в синтетике предобучения (H24, 2026-10-20, 3 сида)

Вопрос: откуда у детектора экземпляров recall на перекрывающихся вызовах? Из перекрытий в синтетической конструкции при предобучении или из самой ветки с декодером? Проверка: R3 (только ветка, modern) предобучен на корпусе без перекрытий (`TSSSL_NOOVERLAP=1`: те же клипы, усиления и число вызовов на смесь, вызовы ставятся только в свободные участки с зазором ≥0.1 с, непоместившиеся отбрасываются; на 1500 смесях: вызовов на смесь 2.38 против 2.51, доля перекрывающихся вызовов 0.00 против 0.57, доля времени с вызовом 0.44 против 0.38). Чтение:
- **Перекрытия в синтетике предобучения дают измеримую часть recall на перекрывающихся вызовах: 0.11 при любом из трёх FAR**, при этом recall на изолированных вызовах не меняется (−0.015, интервал содержит ноль). Эффект специфичен для перекрытий.
- **Большая часть преимущества остаётся и без перекрытий.** Декодер экземпляров опережает покадровый на перекрывающихся на +0.27 без перекрытий против +0.42 с перекрытиями: примерно четверть преимущества относится к конструкции синтетики, остальное к ветке экземпляров и декодеру (и к полевым меткам на FT, которые содержат перекрытия в обоих плечах).
- **Потеря относится именно к пути экземпляров, а не к качеству представления:** покадровый декодер тех же моделей на корпусе без перекрытий даже немного лучше (+0.04), то есть покадровая дорожка наличия на таком корпусе выучивается чище, а способность разделять соседние вызовы ухудшается.
- Это объяснение результата, а не заявка о новизне: у опубликованного Voxaboxen синтетика с перекрытиями тоже есть. В статье это утверждение C6 в ослабленной форме: не «необходимы», а «вносят измеренный вклад».

Оговорки: корпуса различаются по плотности (−5 % вызовов, +6 п.п. времени с вызовом), и выигрыш покадрового декодера на корпусе без перекрытий показывает, что они не идеально согласованы; одна архитектура (R3 modern); 119 перекрывающихся референсов в 17 записях.

## Проверка кандидата на архитектурную новизну: «один токен — один экземпляр» (H25, анализ без обучения, 2026-10-20)

Вопрос рецензии: объясняет ли ограничение событийной ветки (один onset-пик и одна длительность на 20-мс токен; два вызова с началом в одном токене непредставимы) заметную часть оставшихся промахов на перекрывающихся вызовах? Если да, многоэкземплярный выход (слоты/запросы) был бы мотивированным направлением.

R3 modern, декодер экземпляров, рабочие точки dev≤100, 3 сида, на прогон: 119 перекрывающихся референсов, 34.7 промахов (recall 0.709). Расстояние от onset промаха до ближайшего другого onset:

| категория | промахов на прогон | доля |
|---|---|---|
| ≤20 мс (тот же токен, непредставимо) | 2.0 | 6 % |
| ≤ выбранного d_min (0.2–0.7 с): второй пик подавлен минимальным расстоянием между пиками | 10.0 | 29 % |
| прочие, onset-пик ≥0.05 у начала референса есть (экземпляр не прошёл по score/границам) | 12.7 | 37 % |
| прочие, onset-пика нет (чувствительность) | 10.0 | 29 % |

Среди всех 119 перекрывающихся референсов соседний onset ближе 20 мс имеют 3 %, ближе 0.2 с 15 %, ближе 0.5 с 61 %; среди промахов 6 / 26 / 76 %. Близкие начала труднее, но не на уровне токена.

Вывод (диагностическое разбиение, не доказанные причины и не потолок улучшения; «начала ближе 20 мс» и «один токен» не эквивалентны): коллизии начал редки и не мотивируют многоэкземплярный выход как следующий приоритет. Треть промахов это подавление второго пика параметром d_min, который dev-выбор ставит в 0.2–0.3 с под бюджет FA (0.1 с в сетке был): компромисс точности, а не представимости. Подавление второго пика параметром d_min это реальный шаг подавления в нашем декодере, поэтому в рукописи «без NMS боксов / без подавления по IoU», а не «без подавления». Архитектурных работ из этого не следует; SHAP и адаптер не добавляются (SHAP это атрибуция признаков, не механизм; адаптер в аудио-энкодере занят, напр. MTDA-HSED). Файлы: analyze_onset_proximity.py, onset_proximity_R3.json.

## Предлагаемая формулировка вклада

**Что утверждаем.** Компактный (17.8M) детектор вызовов косаток, в котором ветка экземпляров (наличие, onset, длительность; перекрытия разрешены) обучается уже на этапе предобучения на синтетических смесях с перекрытиями, где позиции вставленных вызовов известны по конструкции, а затем дообучается на полевых метках и декодируется без NMS. При бюджетах ≤100 ложных тревог в час он даёт больший recall, чем проверенная нами конфигурация Voxaboxen после полевого FT (BEATs 90M, равный доступ к полевой разметке); при ≥150 FA/ч паритет. Превосходство над Voxaboxen как методом не установлено: его synthetic-чекпоинт без полевого FT при 61 FA/ч даёт 0.816 против наших 0.849, разность +0.033 с интервалом через ноль, а наш полевой FT ухудшил Voxaboxen в этом диапазоне (0.695), то есть подходящий режим FT под recall–FAR для него не найден.

**Что показывает абляция.** (1) Предобучение ветки даёт +0.066 против той же головы, добавленной на FT; на перекрывающихся при FAR 100 +0.068 [+0.025, +0.112]. (2) Дополнительная польза маскированной HuBERT-цели поверх ветки не обнаружена, более простой режим «только ветка» не хуже. (3) Декодер экземпляров даёт наибольший единичный прирост; на перекрывающихся при FAR 100 +0.415 [+0.278, +0.511]. (4) Конфигурация с современным блоком (17.8M) измеримо лучше vanilla-конфигурации (14.8M) в событийном детекторе (+0.05 при FAR 100); эффект относится ко всей конфигурации, включая разницу в размере, и не атрибутирован компонентам. (5) Перекрытия в синтетике предобучения дают 0.11 recall на перекрывающихся вызовах при одинаковом FAR и не меняют recall на изолированных; без них декодер экземпляров всё ещё опережает покадровый на перекрытиях на +0.27 (H24).

**Чем отличается от Voxaboxen.** Не onset + длительность, не перекрывающиеся вызовы как задача и не синтетика с перекрытиями: всё это есть в опубликованном Voxaboxen (шесть синтетических наборов с разной долей перекрытий); отсутствие перекрытий относится только к нашему локальному апрельскому корпусу. Метки по конструкции синтетики тоже известны (DRASDIC). Конкретное отличие: одна событийная ветка в одном направлении, декодирование без soft-NMS и без объединения направлений паросочетанием; компактный энкодер (17.8M), предобученный с событийной супервизией на целевых данных, вместо AudioSet-энкодера 90M. Измерено внутри системы: предобучение ветки и декодер. Не измерено: какая часть разрыва с Voxaboxen приходится на каждое отличие.

**Чего не утверждаем.** Не новую архитектурную идею и не новизну синтетических перекрытий или меток по конструкции. Не «новый HuBERT»: дополнительная польза HuBERT-цели в наших условиях не обнаружена, и финальная система может обходиться без неё. Не превосходство над Voxaboxen как методом (см. выше) и не превосходство при любых бюджетах: при 300 FA/ч Voxaboxen-FT не хуже. Не атрибуцию компонентов блока и размера. Один сид Voxaboxen, 17 записей.
